IMP-01P1 · 阻塞内存诊断已复现 / 源码确认

先恢复草稿，再允许自动保存

影响三个流程的当前草稿。进入页面不应被当作“清空内容”的操作。

当前行为与用户影响

页面从空状态初始化，只在存在一次性的 sessionStorage 恢复指令时加载内容。自动保存约 1.5 秒后执行，空内容触发已有草稿键的删除。

原有稿件 → 刷新或通过普通入口重新进入同一流程 → 未做任何编辑 → 当前草稿可能消失。开发模式的 StrictMode 重放还可能在恢复前消费掉一次性指令。

建议方案 · 待审核

  • 增加“读取中 / 已恢复 / 用户已修改”状态，恢复完成之前不执行保存或删除。
  • 正常进入流程默认恢复当前稿；“新建草稿”作为独立操作，不复用旧稿覆盖槽。
  • 恢复逻辑支持重复执行；在应用恢复数据成功后再消费指令。
  • 区分用户明确清空、未初始化、空白新稿；保存失败提供可见提示。
风险等级依据：影响实际文本留存。前端存储函数单测通过，并不能保证页面进入与恢复顺序正确。

验收标准

  • 三个流程已有稿件时，刷新、普通入口进入、返回再进入，原文和完成稿均可恢复。
  • 等待超过保存防抖时间、快速切页、触发页面离开事件，都不会用空初始状态删除旧稿。
  • 在 StrictMode 开发环境与生产构建中，从首页 / 草稿抽屉恢复均成功，包括同流程恢复。
  • 浏览器存储禁用或配额不足时，页面给出未保存提示，并允许复制 / 导出当前内容。

此处是待执行的验收项，方框不表示已通过。

IMP-02P1 · 阻塞语气变化内存复现 / 模型恢复限制源码确认

保存用户内容，不让配置变化废弃完成稿

生成配置记录内容来源，不能决定已有稿件是否还允许被阅读、编辑与导出。

当前行为与用户影响

完成结果与 topic、type、tone、length、provider、model 的身份完全绑定。仅改语气或模型，下一次自动保存可能将已有完成稿覆盖成 result: null。

原模型不在当前可用列表时，Composer / WeChat 会只恢复参数或清除已恢复结果。已经生成的静态正文因此依赖模型在线和配置可用。

建议方案 · 待审核

  • 稿件使用独立 ID，内容、版本、时间和来源信息作为持久资产保存。
  • “下一次生成的配置”与“当前稿的来源快照”分开；改配置只标记待应用。
  • 模型失效时仍可本地查看、编辑、复制、导出；发起新生成前再选可用模型。
  • 新生成成功后产生新版本；失败或取消时保留用户已确认的版本。

验收标准

  • 完成后修改选题、类型、语气、篇幅、provider 或 model，再保存 / 刷新，原稿仍完整可取回。
  • 模型被移除或 Provider 接口不可用时，已有正文仍支持本地阅读、编辑和导出。
  • 失败、取消、乱序返回不会覆盖用户确认稿；新版本接受前保留前一版。
  • 旧 localStorage 键与草稿格式可迁移并重复读取，不先删旧数据；迁移失败保持原始数据。
  • 用户可创建多篇独立稿件，不再仅靠每个流程的 *-current 槽覆盖历史内容。

迁移原则：新增版本化存储和兼容读取，保持现有 SSE 与旧请求字段兼容；不把“保护来源身份”作为删除文本的依据。

IMP-03P1 · 阻塞源码确认 / 完整交互待验收

让用户能够准确改好一段文字

修改数字、名字、事实与表达，不应必须再调用模型。

当前行为与用户影响

完成后的正文使用 EditableBlock，呈现为普通文本；输入框用于填写 AI 指令，没有直接修改原段落文本的入口。Composer 的普通正文编辑器主要用于生成中或空正文状态。

“更简洁 / 更口语”通过替换标点、词语和空格实现，不能保证语义上的简洁或准确。一个精确小修改也可能引入额外等待与不确定性。

建议方案 · 待审核

  • 增加明确的“编辑正文”模式，优先使用已有 textarea 能力，支持段落与全文编辑。
  • 保留预览模式、复制和导出；手动编辑不依赖模型可用性。
  • AI 改写先展示候选文本，用户选择应用或放弃；提供撤销 / 恢复前一版。
  • 移除伪语义快捷替换，或将其准确命名为格式处理；AI 快捷操作使用真实指令。
  • 异步改写携带版本标识，陈旧结果不覆盖后续手工修改；生成中的编辑策略保持一致。
范围边界：先交付可靠的纯文本编辑和版本保护。富文本、复杂排版编辑器、多人协作不作为本轮前置。

验收标准

  • 三个流程完成稿的正文均可直接修改；模型离线也能精确改一个数字、名字或段落。
  • 中文输入法、换行、空段落、长文输入、撤销及键盘操作正常。
  • AI 候选被拒绝时原文不变；被接受后可恢复原版本，并正确保存。
  • 先发起改写、再手动编辑或切换稿件，旧请求返回不污染当前稿。
  • 微信正文支持明确的全文编辑 / 重生成入口，而不只保留标题与摘要重生成。

  • ComposerPage.tsx · 871—910 行：完成稿切换到段落组件；快捷操作为字符串替换。
  • WeChatPage.tsx · 830—858 行：微信正文段落呈现，无全文编辑器。
  • Caption.tsx · Adapter 正文复用相同段落组件。

已确认的是编辑入口与替换实现；异步乱序、移动端输入法与撤销行为列为修复后的验收要求，不声称已完成浏览器复现。

IMP-04P2 · 紧随修复前后端调用链源码确认

改标签时，围绕用户眼前这篇稿件生成

减少内容错配、隐藏生成步骤与不必要的模型调用。

当前行为与用户影响

Composer 请求仅传选题和生成配置。重生成标签时，后端会重新提炼结构、另生成标题和正文，再据此生成标签，而前端仍显示用户原来的正文。

用户修改过的事实、观点和措辞没有进入这次标签生成。其他块级生成也需要明确当前标题 / 摘要 / 正文之间的上下文关系。

建议方案 · 待审核

  • 请求增加可选当前内容上下文：标题、正文、摘要与稿件版本。
  • 生成标签以当前标题 / 正文为依据；不为该操作额外生成一篇隐藏全文。
  • 标题、摘要、正文重生成明确输入上下文，输出只修改目标块。
  • 旧客户端未传上下文时保留兼容路径；新路径增加字段长度验证和调用量测试。

验收标准

  • 用户编辑正文后重新生成标签，发送给 Provider 的上下文包含最新正文。
  • 新客户端的标签操作不触发隐藏标题 / 正文生成，非目标块内容与版本保持不变。
  • 测试验证调用次数与 prompt 上下文；旧请求和 SSE 事件仍能被现有客户端使用。
  • 通过真实样本文本抽查标签与正文相关性，记录耗时与调用成本变化。
查看代码依据
  • ComposerPage.tsx · 461—469 行：请求没有当前标题 / 正文。
  • compose.py · 187—197、249—270 行：标签重生成重新提炼结构并另生成标题 / 正文。
  • wechat_compose.py · 块级重生成上下文需一并定义。

当前链路确认存在额外调用；具体金额与延迟没有实测，不在本稿给出未经验证的成本节省比例。

IMP-05P2 · 紧随修复规则内存诊断 / 源码确认

把质量提示改成可解释的检查

让用户知道哪里需要调整，并理解建议来自什么规则。

当前行为与用户影响

后端短篇目标为 180–240 字，中篇为 320–450 字；前端检查却统一推荐 500–800 字。按配置生成的内容会收到矛盾提示。

“完读率”按字数公式计算，200 字可得到 100%；互动与覆盖也仅来自词形、问号和标签数量。虽然页面标注“预估仅供参考”，当前数值仍缺少实际效果验证。

建议方案 · 待审核

  • 检查读取平台和目标篇幅，前后端共用清晰的长度规则。
  • 移除无验证依据的完读率 / 互动百分比，改为“长度符合度、结构建议、标签数量”等说明。
  • 将“适合发布”收敛为“基础检查已通过”，避免等同于事实与内容质量审核。
  • 需要人工确认的事实、来源、图片与表达风险单独提示。

验收标准

  • 短篇、中篇、长篇在各自有效区间内不会被要求改成统一长度。
  • 每条建议展示可解释的触发条件；没有真实验证时不展示发布效果百分比。
  • 标题含数字、问号或 emoji 不再自动等同于内容质量高。
  • 空输入、边界字数、重复标签与图片缺失均有一致提示，修改正文后及时更新。

06需要你确定的两项决策

以下属于建议，不是已确认需求
DIR-01产品方向 · 待定

优先服务已有长文素材的创作者

建议主价值：把可信素材转成可编辑、可导出、可追溯的小红书内容包。

建议聚焦的用户与任务

有公众号文章、知识笔记或长文素材，需要持续复用为小红书内容的个人创作者。

主要流程：原文 → 提炼确认 → 生成内容包 → 人工编辑 → 保存版本 → 导出图文。

这条流程能把可控改写、卡片导出和内容留存组合为持续使用的价值。

本轮范围取舍

  • 保留公众号与原创创作入口，优先保障三条流程共有的保存 / 编辑能力。
  • 先完善素材复用与图文交付；账号、云同步、自动发布、多人协作后置。
  • 模型选择逐步收纳为高级配置，普通用户优先看到任务与内容结果。
  • 是否调整首页主入口和宣传文案，由本项审核意见决定。
本项不意味着删除已有流程。建议批准的是投入顺序与核心定位；如需继续三条流程同等投入，可在备注中明确。
QA-01验收要求 · 待定

验收一篇稿件的完整使用过程

函数测试之外，验证内容能否从生成一直走到重新打开与发布交付。

建议补充的测试

  • 真实 React 页面测试：进入、恢复、修改、切配置、返回、刷新、再次编辑。
  • 失败路径：生成中断、模型移除、存储配额不足、改写结果乱序、旧草稿迁移。
  • 浏览器检查：Chrome / Edge / Safari / iOS Safari，含 390、768、920、1024、1280、1440 宽度与键盘导航。
  • 服务检查：实际 Provider 完整调用和容器构建 / 启动；单独记录环境阻塞与未验收项。

建议的产品效果验证

准备约 20 篇有代表性的素材作为首轮样本集，覆盖观点、知识、案例、教程与长短边界；样本数量是建议，待审核确定。

  • 记录核心事实保留情况和新增无依据内容。
  • 记录人工修改量、编辑耗时、单篇模型成本与失败率。
  • 由使用者判断是否愿意发布，记录实际发布 / 复用反馈。
  • 先建立基线，再确定可发布率与成本目标，不预设未经测量的改善比例。

签字条件建议

  • 已批准 P1 的验收项全部通过，未发现稿件删除、覆盖或无法恢复的路径。
  • 产物可准确编辑和导出；样本内容经人工检查，遗留问题有明确记录。
  • 测试结果绑定实际代码版本，并更新发布文档；浏览器 / Provider / 容器未验证时不得写为通过。
