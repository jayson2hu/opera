# Opera UI 全面设计探索（Phase 01）

> 日期：2026-09-15  
> 原型入口：`/explore`  
> 状态：供产品负责人评审；不代表选型完成，不进入大规模业务改造。

## 1. 这次真正要决定什么

表面问题是“Opera 应该采用哪一种 UI 风格”，真正问题是：

> 哪一种交互模型，最能帮助独立创作者理解 AI 的工作过程、在关键节点做判断，并把结果高效地变成可交付作品？

三套方案因此不是换皮，而是三个不同的产品模型：

- A：以任务、作品和状态为中心的专业控制台。
- B：以 Agent 推进、用户确认、Artifact 接管为中心的 AI 原生工作台。
- C：以作品舞台、沉浸画布和品牌仪式感为中心的高级创作空间。

## 2. 当前 Opera 产品分析

### 2.1 产品定位

Opera 是一个 AI 辅助内容创作工作台，帮助创作者完成公众号与小红书内容的原创、改写、编辑和交付。

当前边界：

- 支持公众号文章创作、公众号转小红书、小红书原创三条流程。
- 支持本地草稿、版本、候选内容确认、段落编辑、复制和卡片导出。
- 当前无需登录，数据主要保存在浏览器本地。
- 不是内容发布平台，不连接公众号或小红书账号，不自动发布。
- 不是数据分析、多人协作、内容日历或多账号管理平台。

### 2.2 用户角色

主用户：高频但资源有限的独立创作者。

典型画像：

- 知识、职场、教育、商业、生活方式领域。
- 有公众号存量内容，需要低成本复用到小红书。
- 有观点和经验，但不总能快速组织成长文或社交内容。
- 需要效率，也重视内容真实性、个人语气和最终控制权。
- 粉丝规模通常约 1k–50k，没有完整内容团队。

次级角色：

- 公众号新手：需要从模糊想法获得结构和写作引导。
- 内容运营者：更关注批量处理、状态扫描和稳定交付。
- 视觉型创作者：更关注卡片顺序、版式预览和品牌表达。

### 2.3 核心业务流程

#### 流程 1：公众号转小红书

1. 粘贴公众号长文。
2. 选择语气、目标篇幅和模型。
3. AI 提取核心观点。
4. 用户确认或调整观点。
5. 生成封面标题、卡片、正文和标签。
6. 用户编辑、选择、复制或导出。

#### 流程 2：小红书原创

1. 输入选题或想法。
2. 选择内容类型、语气、篇幅和模型。
3. 生成标题、正文、标签与配图建议。
4. 用户编辑、局部重生成、预览和复制。

#### 流程 3：公众号创作

1. 输入选题或素材。
2. 选择文章类型、语气、篇幅和模型。
3. 生成标题、摘要和正文。
4. 用户进行段落级精修、保存版本和转换为小红书改写稿。

三条流程的共同骨架是：输入意图 → 配置方向 → AI 生成 → 人工审核 → 编辑 → 交付。

### 2.4 当前页面结构

```text
全局 Header
├── 品牌 / 返回首页
├── 模型状态与选择
├── 草稿抽屉
├── 偏好设置
└── 本地用户菜单

首页
├── 三条流程入口
├── 创作天数 / 连续创作信息
└── 最近草稿

流程页 × 3
├── 返回栏 / 草稿工作区栏
├── 输入和参数配置
├── 生成进度
├── 候选内容确认
├── 编辑器 / 预览
├── 质量检查
└── 复制 / 导出动作
```

### 2.5 当前 UI 问题

1. 信息层级友好但偏松，专业高频用户需要扫描多个大卡片才能判断当前状态。
2. Header、首页、返回栏和页面内部步骤都承担导航，用户需要在多套导航语义之间切换。
3. 三条流程已有大量共同能力，但页面视觉骨架仍不完全一致，学习不能充分迁移。
4. 草稿、版本、候选、模型、质量检查和交付动作分散，缺少统一“作品工作台”心智。
5. AI 的中间过程虽然已开始可见，但仍更像系统状态，不完全像可理解、可干预的协作过程。
6. 现有暖橙、紫、绿三色区分流程，容易识别，但品牌表达更接近通用创作工具。
7. 移动端能完成任务，但复杂编辑和多结果比较仍需要更明确的优先级折叠。

### 2.6 信息架构问题

当前一级对象是“功能流程”，用户真实关心的一级对象往往是“我正在完成的作品”。

建议未来信息架构从：

```text
首页 → 选功能 → 进入流程 → 找草稿 / 找结果
```

逐步转向：

```text
作品工作区
├── 新建作品（选择目标）
├── 进行中的作品
├── 最近完成与导出
└── 每个作品内的输入、Agent 过程、版本、编辑和交付
```

流程仍然存在，但成为“作品的创建方式”，不再是用户必须记住的产品结构。

## 3. 方案 A：Signal Desk / 现代 SaaS 企业风格

### 3.1 设计理念

把 Opera 设计成可信赖的内容生产控制台。每个作品有清晰状态，所有动作可预测，复杂信息可快速扫描。

### 3.2 用户体验目标

- 让高频创作者在 5 秒内知道哪些作品正在进行、哪些待审核、哪些可交付。
- 让三条创作流程共享同一套编辑、版本和导出骨架。
- 提高信息密度，同时保持操作层级和状态清晰。

### 3.3 色彩体系

| 角色 | 色值 | 用途 |
|---|---|---|
| Graphite | `#111318` | 品牌、主按钮、强文本 |
| Indigo | `#5E6AD2` | 选中态、进度、AI 操作 |
| Canvas | `#F5F6F8` | 页面背景 |
| Surface | `#FFFFFF` | 卡片、面板、工作区 |
| Success | `#38A56B` | 已保存、可交付、完成 |

### 3.4 字体方案

- UI：Inter、系统无衬线。
- 中文：PingFang SC / Noto Sans SC。
- 状态和元数据：等宽字体，小写或全大写。
- 基础字号 12–14px，标题 24–32px，紧凑行高。

### 3.5 Layout 布局

- 固定左侧栏 216–232px。
- 顶部全局命令栏支持搜索、创建和状态。
- Dashboard 使用统计卡、作品表格和快速流程两列布局。
- 核心页使用输入 / AI 提取 / 输出三栏。

### 3.6 导航设计

- 一级：Overview、Content Desk、All Drafts、Templates。
- 二级：作品内 Compose、Versions、Quality Checks。
- 全局 `⌘K` 搜索作品、来源和动作。

### 3.7 首页设计

- 顶部问候和新建作品主操作。
- 四个高密度状态指标。
- 最近作品表格展示流程、状态、更新时间。
- 快速开始三条现有流程。

### 3.8 核心业务页面

三栏协作台：

1. Source & direction：原文、目标、语气和篇幅。
2. Key ideas：AI 提取观点和人工确认。
3. Output package：标题、卡片、正文、标签和导出。

### 3.9 数据展示方式

- 紧凑表格、状态圆点、趋势数字、低装饰图表。
- 不展示无法验证的“传播分数”或“完读率预测”。
- 质量检查使用规则、来源和明确提示。

### 3.10 组件规范

- 圆角：6 / 8 / 10px。
- 边框：1px 中性灰；默认弱阴影。
- 控件高度：28 / 32 / 36px。
- 状态色仅承担语义，不作大面积装饰。
- 焦点、悬停、选中和禁用状态必须明显。

## 4. 方案 B：Agent Canvas / AI 原生产品风格

### 4.1 设计理念

让 Agent 负责推进流程，让用户在真正影响结果的节点确认、纠正或接管。对话是工作流，Artifact 是最终作品。

### 4.2 用户体验目标

- 新手只需描述目标，不必先理解所有配置项。
- 用户能看到 AI 正在做什么、为什么停下来，以及下一步需要什么。
- 生成过程、观点确认、编辑结果和交付保持在同一个上下文。

### 4.3 色彩体系

| 角色 | 色值 | 用途 |
|---|---|---|
| Charcoal | `#1E201D` | 会话侧栏、强文本 |
| Warm Paper | `#F4F1EA` | 主背景、阅读空间 |
| Clay | `#D97757` | Agent、主动作、关键确认 |
| Sage | `#8EA68F` | 完成、保存、可信状态 |
| Artifact | `#FBFAF6` | 内容成品画布 |

### 4.4 字体方案

- UI：Avenir Next / Inter / 系统无衬线。
- 作品与 Agent 长文本：Iowan Old Style、Noto Serif SC、Georgia。
- 元数据：等宽字体。
- 基础字号比 A 大一级，保持对话可读性。

### 4.5 Layout 布局

- 左侧会话 / 作品历史。
- 新建首页使用居中自然语言输入框。
- 核心页左侧为 Agent 对话和过程，右侧为可编辑 Artifact。
- 小屏幕按“对话 → 作品”分段切换，不强行保留双栏。

### 4.6 导航设计

- 新建对话、搜索、最近作品。
- 作品即会话，会话保存完整创作上下文。
- 模型选择弱化为 Agent 能力设置，不成为首页主任务。

### 4.7 首页设计

- 以“What will we create today?”开始。
- 用户可输入自然语言，也可选择三条任务建议。
- 下方展示可继续的作品，而不是传统统计 Dashboard。

### 4.8 核心业务页面

- Agent 明确说明计划：读取 → 理解 → 确认观点 → 创建内容包。
- 核心观点是强制人工确认点。
- Artifact 独立承载标题、卡片、正文和标签，支持复制、预览和编辑。
- 用户能继续对话要求调整，也能直接编辑 Artifact。

### 4.9 数据展示方式

- Agent 时间线展示过程状态、输入来源和等待原因。
- 结构化引用卡展示 AI 从原文保留了什么。
- 数据只解释作品状态和质量检查，不强调“运营仪表盘”。

### 4.10 组件规范

- 圆角：8 / 12 / 14px。
- Warm Paper 表面，Clay 仅用于 Agent 与主确认动作。
- 用户消息和 Agent 消息保持清晰角色差异。
- 所有 Agent 状态必须支持完成、运行、等待用户、错误、停止。
- Artifact 编辑必须保留候选应用和版本安全机制。

## 5. 方案 C：Opera Atelier / 高级商业产品风格

### 5.1 设计理念

把 Opera 设计成私人数字创作工作室。通过光、空间、节奏和编辑美学，降低工具感，提高作品价值感。

### 5.2 用户体验目标

- 建立明显区别于通用 AI 工具的品牌记忆。
- 让深度创作更专注，减少页面和设置对内容的干扰。
- 在关键节点创造“作品完成”的仪式感。

### 5.3 色彩体系

| 角色 | 色值 | 用途 |
|---|---|---|
| Obsidian | `#07080B` | 主背景 |
| Electric Violet | `#8B5CF6` | 空间光感、创意强调 |
| Acid Lime | `#D6FF66` | 主动作、完成、高光 |
| Pearl | `#F6F3FF` | 主文本、作品表面 |
| Smoke | `#777A84` | 次级信息 |

### 5.4 字体方案

- 展示：Iowan Old Style / 高品质衬线字体。
- UI：Helvetica Neue / Inter。
- 元数据：等宽字体、较大字距。
- 大标题使用 44–72px，正文保持低密度和宽松行高。

### 5.5 Layout 布局

- 64px 悬浮侧轨。
- Dashboard 使用大幅 Hero 和不对称 Bento 布局。
- 核心页使用 Outline / Artboard / Inspector 空间化结构。
- 底部 Command Dock 提供模式和全局命令。

### 5.6 导航设计

- 图标侧轨弱化页面感。
- Command Palette 是主要快速通路。
- Canvas、Agent、Versions 作为作品模式，不作为分散页面。

### 5.7 首页设计

- 强品牌欢迎语和“开始一件作品”主入口。
- 大型作品卡突出继续创作。
- 创作节奏、最近作品、品牌原则组成视觉 Bento。

### 5.8 核心业务页面

- 中央 Artboard 直接呈现卡片成品。
- 左侧 Outline 展示内容叙事结构。
- 右侧 Inspector 控制 Agent 建议、字体、视觉氛围。
- Focus 模式可隐藏工具栏，进入纯作品编辑。

### 5.9 数据展示方式

- 大数字、极简进度条、编辑式作品缩略图。
- 只呈现能增强创作节奏的数据，不构建传统运营 Dashboard。

### 5.10 组件规范

- 圆角：9 / 14 / 16 / 24px。
- 深色玻璃层、空间光晕、低透明度网格。
- 交互优先使用平滑位移、模糊和光带，必须支持减少动态偏好。
- 高亮色面积受控，确保长时间编辑舒适度。

## 6. 三方案对比

| 维度 | A Signal Desk | B Agent Canvas | C Opera Atelier |
|---|---|---|---|
| 上手清晰度 | 很高 | 高 | 中 |
| 信息密度 | 很高 | 中高 | 中低 |
| AI 过程透明 | 中 | 很高 | 高 |
| 人工接管 | 高 | 很高 | 高 |
| 品牌差异化 | 中 | 高 | 很高 |
| MVP 实施效率 | 很高 | 高 | 中低 |
| 主要风险 | 通用 SaaS 感 | 对话过长、Agent 越权 | 视觉成本与可读性 |

## 7. 推荐方向

推荐选择 **方案 B：Agent Canvas** 作为正式方向。

理由：

1. Opera 的真正差异化来自“AI 如何与创作者协作”，不是再做一个更漂亮的表单编辑器。
2. B 最直接地解决当前核心阻力：AI 过程难理解、用户干预点分散、生成与作品割裂。
3. B 对新手更自然，同时保留 Artifact 供专业用户直接编辑和接管。
4. 当前已有提取观点确认、候选应用、版本和局部重生成能力，迁移到 B 的技术基础已经存在。

建议融合规则：

- 以 B 的 Agent 对话和 Artifact 双栏为主干。
- 吸收 A 的作品列表、状态扫描、版本与质量检查密度。
- 将 C 的品牌语汇用于营销页、登录页、空状态和作品完成时刻，不把整套重视觉系统直接带入所有编辑页面。

## 8. 最小验证计划

在正式开发前，用当前原型完成 5–8 位目标用户测试：

1. 用户能否在 30 秒内开始“公众号转小红书”。
2. 用户是否理解 Agent 为什么在观点确认处暂停。
3. 用户能否修改一个观点并继续生成。
4. 用户能否区分“对话请求调整”和“直接编辑成品”。
5. 用户能否找到版本、复制和导出。
6. 对比 A/B 后，用户完成同一任务所需时间和回退次数。

最可能改变推荐的证据：如果高频创作者普遍认为对话降低扫描效率，并明显偏好并行作品管理，则应把主方向调整为 A，并仅保留 B 的关键 Agent 确认节点。

## 9. 原型实现与运行

原型隔离在前端 `/explore` 路径：

```bash
cd opera-app
npm ci
npm run dev
```

打开：

- 对比页：`http://localhost:5173/explore`
- A Dashboard：`http://localhost:5173/explore?concept=a&screen=dashboard`
- B 核心工作台：`http://localhost:5173/explore?concept=b&screen=workspace`
- C 设置页：`http://localhost:5173/explore?concept=c&screen=settings`

根路径的现有业务页面和业务逻辑保持不变；当前页脚增加了“UI 设计探索”入口。

## 10. 已知边界

- 原型使用静态演示数据，不调用生成 API，不写入正式草稿。
- 登录页只验证未来视觉和信息结构，当前产品仍为免登录、本地草稿模式。
- 原型用于方向评审，不代表账号、云同步、分析或发布功能已进入范围。
- 下一阶段必须等待产品负责人选择方向后再拆分正式组件与迁移计划。

## 11. 验证记录

- TypeScript + Vite production build：通过。
- 前端单元测试：21 个测试文件、149 项通过（含对比页内容检查，以及 A/B/C 各 4 个页面的独立深链接渲染检查）。
- ESLint：0 问题；首轮发现的 Hook 写法问题已修复并复跑通过。
- 路由启动检查：根路径、对比页与 A/B/C 各 4 个页面的独立 URL 均返回 HTTP 200。
- Chromium 实际浏览器复核：对比页与 A/B/C 各 4 个页面（共 13 个桌面场景）全部返回 HTTP 200，无页面异常、无控制台错误、无整页横向溢出。
- 响应式复核：对比页在 860px 与 390px 视口无整页横向溢出；复杂工作台在窄屏内使用独立横向浏览区，避免破坏设计稿的桌面构图。
- 关键交互复核：A 登录概念页可进入 Dashboard，B 的观点确认可更新 Agent 状态，C 的 Focus / Canvas 模式可切换；复核中发现并修正了 B 底部输入框遮挡观点确认按钮的问题。
- 已逐张检查对比页、三套 Dashboard、B/C 核心工作台截图；本次一次性无头浏览器环境未安装中文字库，因此中文像素级字形仍应在产品负责人的本机浏览器中做最终确认。
